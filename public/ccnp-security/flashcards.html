  1. 2.1 What is the one deciding question for whether a security device can block traffic?

    Is it inline? Only a device the real packet passes through can drop it. Passive (SPAN, TAP, ERSPAN) and inline tap mode can only alert.

    review in the notes →
  2. 2.1 IPS vs. IDS in one line each.

    IPS detects and blocks (must be inline). IDS detects and alerts only (usually passive, fed by SPAN or TAP).

    review in the notes →
  3. 2.1 How does a stateful firewall let return traffic in without an ACL for it?

    It records each session (e.g. SYN, SYN-ACK, ACK) in its state table and permits packets that match a session your side started. UDP and ICMP get pseudo-state via idle timeouts.

    review in the notes →
  4. 2.1 Stateless ACL vs. stateful firewall?

    A stateless ACL judges each packet alone. A stateful firewall judges each packet in the context of its conversation.

    review in the notes →
  5. 2.1 What does an NGFW add on top of a stateful firewall?

    Integrated IPS, AVC (application visibility and control), URL filtering, malware defense with sandboxing, user identity (ISE or AD) and Security Intelligence reputation blocking.

    review in the notes →
  6. 2.1 Name the four IPS detection approaches.

    Signature (known patterns), anomaly/behavior (deviation from baseline), reputation (bad IPs, URLs, files), and policy (anything that violates a rule, e.g. SMBv1).

    review in the notes →
  7. 2.1 Why does signature-based IPS miss zero-day attacks?

    It only matches patterns that already have a signature. Until Talos writes and publishes a rule, a brand-new attack has nothing to match.

    review in the notes →
  8. 2.1 False positive vs. false negative on an IPS: which one is the outage and which is the breach?

    False positive = legitimate traffic dropped (business outage). False negative = an attack gets through (breach).

    review in the notes →
  9. 2.1 List the FTD base intrusion policies from least to most aggressive.

    Connectivity Over Security, Balanced Security and Connectivity (recommended start), Security Over Connectivity, Maximum Detection (testing only).

    review in the notes →
  10. 2.1 What engine provides IPS on Cisco Secure Firewall, and who writes its rules?

    Snort (Snort 3 on current FTD). Rules come from Cisco Talos.

    review in the notes →
  11. 2.1 Where does Security Intelligence sit in FTD processing, and why does that matter?

    It's evaluated before deep inspection, so known-bad IPs, URLs and domains are blocked cheaply and early.

    review in the notes →
  12. 2.1 Routed vs. transparent firewall mode?

    Routed: a Layer 3 hop, an IP per interface, hosts use it as gateway. Transparent: a Layer 2 bump in the wire using bridge groups (management IP on the BVI), inserted without re-addressing.

    review in the notes →
  13. 2.1 Which FTD IPS interface mode is physically inline but can never block?

    Inline set in tap mode. Snort gets a copy and the original packet is forwarded untouched. Use it to tune before going truly inline.

    review in the notes →
  14. 2.1 What is an FTD inline set?

    Two interfaces bound together as a pair. Traffic enters one and leaves the other, so Snort can drop bad packets: a true inline IPS. It supports fail-open options and hardware bypass on supported modules.

    review in the notes →
  15. 2.1 When would you use passive ERSPAN instead of passive (SPAN)?

    When the sensor is routed hops away. ERSPAN GRE-encapsulates the mirrored traffic so it can cross Layer 3. It's routed mode only and still alert-only.

    review in the notes →
  16. 2.1 TAP vs. SPAN?

    A TAP is hardware that copies every frame and never oversubscribes. A SPAN session is free and flexible but can drop frames when busy.

    review in the notes →
  17. 2.1 What HA modes does FTD support, and which ASA-only mode is the trap answer?

    FTD: active/standby failover and clustering. Active/active failover exists only on ASA in multiple context mode.

    review in the notes →
  18. 2.1 FTD multi-instance is the counterpart of which ASA feature?

    ASA multiple context mode. Both split one box into independent virtual firewalls.

    review in the notes →
  19. 2.1 Fail-open vs. fail-closed?

    Fail-open keeps forwarding uninspected traffic when the engine fails (availability wins). Fail-closed stops forwarding (security wins). It's a business decision.

    review in the notes →
  20. 2.1 ASA vs. FTD: where do IPS, AVC, URL and malware features live?

    Built into FTD. ASA is stateful firewall + NAT + VPN; its old FirePOWER add-on module is end-of-life.

    review in the notes →
  21. 2.1 FMC vs. FDM vs. Security Cloud Control?

    FMC: many FTDs (on-prem or virtual; also cloud-delivered FMC). FDM: one FTD, on-box. Security Cloud Control (formerly CDO): SaaS management across ASA, FTD, Multicloud Defense and more.

    review in the notes →
  22. 2.1 Which Cisco product is the cloud-native firewall/IPS for public cloud workloads?

    Cisco Multicloud Defense: SaaS-managed gateways for ingress, egress and east-west traffic across clouds.

    review in the notes →
  23. 2.1 Which Cisco product delivers firewall + IPS to remote users from the cloud?

    Cisco Secure Access (SSE): cloud-delivered firewall with IPS, SWG, DNS-layer security, CASB and ZTNA.

  24. 2.1 How do you get firewall and IPS in a branch without an extra appliance?

    On the IOS XE router: Zone-Based Firewall plus Snort IPS (UTD container). Meraki MX is the cloud-managed alternative.

  25. 2.1 What is a hybrid mesh firewall?

    Many enforcement points of different form factors (appliance, virtual, cloud-native, cloud-delivered, router-embedded) managed as one policy.

  26. 2.1 ZBFW: can an interface in a zone talk to an interface that is in no zone?

    No. Zone to no-zone traffic is always dropped. Different zones need a zone-pair policy; the same zone is allowed by default.

    review in the notes →
  27. 2.1 ZBFW actions: inspect vs. pass vs. drop?

    inspect is stateful (return traffic allowed automatically). pass is stateless and one-way (needs a mirror rule). drop discards.

    review in the notes →
  28. 2.1 Two ways an NGFW handles malware hidden in TLS?

    Decryption policy (Decrypt-Resign outbound, Decrypt-Known Key for your own servers) or the Encrypted Visibility Engine, which fingerprints the TLS handshake without decrypting.

    review in the notes →
  29. 2.1 Where does a firewall do east-west work?

    In the data center (and campus): segmentation between app tiers or user groups, stopping lateral movement.

    review in the notes →
  30. 2.2 Why ship logs off the device?

    Local logs rotate and overwrite, and attackers delete them to hide. A central, access-controlled copy survives both.

    review in the notes →
  31. 2.2 Why does NTP matter to security monitoring?

    Correlating firewall, switch and server logs needs matching timestamps. Authenticate NTP so an attacker can't skew time.

    review in the notes →
  32. 2.2 Syslog severities 0 to 7?

    0 Emergency, 1 Alert, 2 Critical, 3 Error, 4 Warning, 5 Notice, 6 Informational, 7 Debugging. Lower number = more severe.

    review in the notes →
  33. 2.2 logging trap 4 sends which severities?

    0 through 4: the configured level and everything more severe.

    review in the notes →
  34. 2.2 Classic syslog transport vs. secure syslog?

    Classic: UDP 514, cleartext and unreliable. Secure: TLS on TCP 6514.

    review in the notes →
  35. 2.2 SNMPv3 security levels, and which one to use?

    noAuthNoPriv, authNoPriv, authPriv. Use authPriv: authentication (SHA) plus encryption (AES).

    review in the notes →
  36. 2.2 SNMP trap vs. inform?

    A trap is fire-and-forget. An inform is acknowledged and retransmitted until confirmed.

    review in the notes →
  37. 2.2 MIB vs. OID?

    The MIB is the tree (database) of everything a device exposes. An OID is the exact address of one item, e.g. 1.3.6.1.2.1.1.1.0 = sysDescr.

    review in the notes →
  38. 2.2 SNMP ports?

    Polls to the agent on UDP 161. Traps and informs to the manager on UDP 162.

    review in the notes →
  39. 2.2 Is NetFlow a packet capture?

    No. It's conversation metadata: key fields (5-tuple, ingress interface, ToS) plus counters (bytes, packets, time). No payload.

    review in the notes →
  40. 2.2 NetFlow v5 vs. v9 vs. IPFIX?

    v5: fixed format, IPv4 only. v9: template-based, extensible. IPFIX: the IETF standard based on v9 ("v10"), UDP 4739.

    review in the notes →
  41. 2.2 Flexible NetFlow building blocks?

    Flow record (match = key fields, collect = non-key), flow exporter (where to send), flow monitor (record + exporter + cache), applied to an interface.

    review in the notes →
  42. 2.2 What is NSEL?

    NetFlow Secure Event Logging: ASA/FTD export firewall connection events (flow-create, flow-teardown, flow-denied) as NetFlow v9.

    review in the notes →
  43. 2.2 SPAN vs. RSPAN vs. ERSPAN?

    SPAN: same switch. RSPAN: across L2 switches via an RSPAN VLAN. ERSPAN: GRE-encapsulated across an L3 network.

    review in the notes →
  44. 2.2 Model-driven telemetry: dial-in vs. dial-out?

    Dial-in: the collector connects and subscribes (NETCONF, gNMI). Dial-out: the device initiates the stream to a receiver (gRPC).

    review in the notes →
  45. 2.2 Why is streaming telemetry better than SNMP polling at scale?

    Devices push structured YANG data periodically or on change: near-real-time, no MIB parsing, more data points, lower device CPU.

  46. 2.2 Four FMC event types?

    Connection, Security Intelligence, intrusion, and file & malware events.

  48. 2.2 What was Stealthwatch renamed to, and what kind of tool is it?

    Cisco Secure Network Analytics: on-prem NDR that turns NetFlow/IPFIX into behavioral detections.

  49. 2.2 Secure Network Analytics: Flow Collector vs. Flow Sensor?

    Flow Collector receives and stores flow records. Flow Sensor generates flow records from a SPAN/TAP where devices can't export NetFlow.

  50. 2.2 What does UDP Director / Cisco Telemetry Broker do?

    Adds handshake-derived fields to flow records so Secure Network Analytics can spot malware in encrypted traffic without decrypting it, and audit crypto in use.

  52. 2.2 What extra context does Secure Client NVM add to flow data?

  53. 2.2 Where did Secure Cloud Analytics go?

  54. 2.2 ISE vs. pxGrid?

    ISE is the context broker (it knows user, device, posture, location). pxGrid is the publish/subscribe fabric that shares that context.

  55. 2.2 What is Rapid Threat Containment?

  56. 2.2 SIEM vs. SOAR?

    SIEM ingests, correlates and alerts (the brain). SOAR automates the response with playbooks (the hands).

  57. 2.2 EDR vs. NDR vs. XDR?

  61. 2.3 What do ARP, DHCP, STP, DTP, CDP and VTP have in common from a security point of view?

    None of them authenticate by default. The switch and the hosts believe whatever frame arrives, so the attack pattern is: forge a control message, poison a table, redirect traffic.

    review in the notes →
  62. 2.3 Name the four defense moves for Layer 2 attacks.

    Remove (turn the protocol off where unneeded), limit (cap how much), validate (check against trusted data) and contain (shrink the blast radius).

    review in the notes →
  63. 2.3 The three questions to ask about every switch port?

    Who should be on the other end? What is it allowed to say? If it lies, how far does the lie travel, and how will I know?

    review in the notes →
  64. 2.3 Where is the trust boundary for DHCP snooping, DAI and BPDU Guard?

    At the access edge: user-facing ports are untrusted; uplinks toward infrastructure you control are trusted.

    review in the notes →
  65. 2.3 Why is VLAN segmentation called a blast-radius control?

    A Layer 2 attack (ARP spoofing, MAC flood, broadcast storm) stays inside its VLAN. Crossing VLANs requires routing, where firewalls and ACLs enforce policy.

    review in the notes →
  66. 2.3 Ideal relationship between VLANs and IP subnets?

    One to one: each VLAN (broadcast domain) carries exactly one subnet.

    review in the notes →
  67. 2.3 What does "Negotiation of Trunking: On" on an access port mean?

    The port still runs DTP and can become a trunk if a device asks: the hole that enables switch-spoofing VLAN hopping.

    review in the notes →
  68. 2.3 DTP: dynamic auto + dynamic auto forms what?

    An access link. Neither side initiates. It's luck, not security: an attacker sending desirable DTP still gets a trunk.

    review in the notes →
  69. 2.3 DTP: dynamic auto + dynamic desirable forms what?

    A trunk. Desirable actively asks; auto agrees.

    review in the notes →
  70. 2.3 What does switchport nonegotiate do, and what does it need?

    Stops the port sending DTP. It requires a hard-coded mode (access or trunk); a nonegotiate trunk needs the far end hard-coded to trunk too.

    review in the notes →
  71. 2.3 Switch-spoofing VLAN hopping: how does it work and how do you stop it?

    The attacker sends DTP and the port becomes a trunk carrying every VLAN. Stop it with switchport mode access + switchport nonegotiate on every access port.

    review in the notes →
  72. 2.3 What does the switchport host macro configure?

    switchport mode access, spanning-tree portfast and no channel-group. Access ports only, never uplinks.

    review in the notes →
  73. 2.3 Double-tagging VLAN hopping: the two conditions it needs?

    The attacker's access port is in the native VLAN, and the native VLAN crosses the trunk untagged.

    review in the notes →
  74. 2.3 Why is double tagging a one-way attack?

    Only the attacker's frames get the stripped-outer-tag trick. Replies from the victim are tagged normally and have no path back.

    review in the notes →
  75. 2.3 Three fixes for double tagging?

    Native VLAN = an unused dead VLAN with no hosts (e.g. 999), tag the native VLAN (vlan dot1q tag native), and prune it where possible.

    review in the notes →
  76. 2.3 What log appears when native VLANs differ on a trunk?

    %CDP-4-NATIVE_VLAN_MISMATCH (and STP RECV_PVID_ERR). Both ends must match.

    review in the notes →
  77. 2.3 Default allowed VLANs on a trunk, and the fix?

    1-4094. Use switchport trunk allowed vlan 40,50,99 so only needed VLANs cross the link.

    review in the notes →
  78. 2.3 How does VTP decide which VLAN database wins?

    The highest configuration revision in the domain wins, which is why a stray switch can wipe production VLANs (the VTP bomb).

    review in the notes →
  79. 2.3 Three ways to contain the VTP risk?

    VTP transparent mode, VTPv3 (only the primary server can change the database, plus a password), or run no VTP.

    review in the notes →
  80. 2.3 What does a MAC flooding attack achieve?

    It fills the CAM table, so the switch floods unknown unicast out every port in the VLAN, letting the attacker sniff traffic meant for others.

    review in the notes →
  81. 2.3 The command that is easiest to forget when configuring port security?

    The bare switchport port-security, which actually enables the feature.

    review in the notes →
  82. 2.3 Port security default maximum MACs and default violation mode?

    Maximum 1; violation shutdown.

    review in the notes →
  83. 2.3 Port security on a port in dynamic auto?

    Rejected: "Command rejected: ... is a dynamic port." Hard-code switchport mode access first.

    review in the notes →
  84. 2.3 protect vs. restrict vs. shutdown?

    protect: drop silently. restrict: drop + log/trap + counter. shutdown: err-disable the port + log/trap + counter.

    review in the notes →
  85. 2.3 Which violation mode keeps the port up but still tells you about the violation?

    restrict.

    Secure-shutdown and err-disabled with reason psecure-violation.

    errdisable recovery cause psecure-violation + errdisable recovery interval <sec>. Off by default; default interval 300 s.

    review in the notes →
  88. 2.3 Sticky vs. static secure MACs?

    Sticky learns the MAC and writes it into the running config (save it). Static is typed in manually.

    review in the notes →
  89. 2.3 Port security max for a port with an IP phone and a PC behind it?

    Usually 2 or 3: the PC and the phone (the phone's MAC can be learned in both the voice and data VLAN).

    review in the notes →
  90. 2.3 What port security cannot stop?

    VLAN hopping, ARP spoofing, and MAC spoofing of an allowed address. Real identity needs 802.1X or MAB with ISE.

    review in the notes →
  91. 2.3 STP manipulation attack?

    Sending superior BPDUs to become root bridge: traffic flows through the attacker (MITM), or constant re-elections cause DoS.

    review in the notes →
  92. 2.3 BPDU Guard?

    On PortFast edge ports: any BPDU received → port err-disabled. Global: spanning-tree portfast bpduguard default.

    review in the notes →
  93. 2.3 Root Guard?

    On ports where the root must never appear: a superior BPDU puts the port in root-inconsistent (blocking); it recovers automatically when they stop.

    review in the notes →
  94. 2.3 Loop Guard?

    On root/alternate ports between switches: if BPDUs stop arriving (unidirectional link) the port goes loop-inconsistent instead of forwarding.

    review in the notes →
  95. 2.3 Why is BPDU Filter dangerous?

    It stops sending and receiving BPDUs, effectively disabling STP on the port, so a loop through it isn't detected.

    review in the notes →
  96. 2.3 Two DHCP attacks DHCP snooping addresses?

    Rogue DHCP server (hands out its own gateway/DNS: MITM) and DHCP starvation (exhausts the pool).

    review in the notes →
  97. 2.3 What does DHCP snooping do with an OFFER or ACK on an untrusted port?

    Drops it. Server messages are only accepted on trusted ports.

    review in the notes →
  98. 2.3 Which DHCP snooping port is trusted?

    The uplink toward the real DHCP server or relay (ip dhcp snooping trust). Everything else stays untrusted (the default).

    review in the notes →
  99. 2.3 Two global commands DHCP snooping needs?

    ip dhcp snooping and ip dhcp snooping vlan <list>.

    review in the notes →
  100. 2.3 What does the DHCP snooping binding table contain?

    MAC, IP, lease, VLAN and port for each lease. DAI and IP Source Guard validate against it.

    review in the notes →
  101. 2.3 DHCP stops working after enabling snooping with a relay upstream. Likely cause?

    Option 82 inserted by the switch. Fix: no ip dhcp snooping information option (or trust option 82 on the relay).

    review in the notes →
  102. 2.3 How do you defeat DHCP starvation?

    ip dhcp snooping limit rate on user ports (err-disables floods) plus port security to cap MACs.

    review in the notes →
  103. 2.3 What does DAI validate, and against what?

    ARP packets on untrusted ports, checking the sender IP-to-MAC pair against the DHCP snooping binding table.

    review in the notes →
  104. 2.3 DAI drops ARP from a server with a static IP. Fix?

    Create an ARP ACL for its IP/MAC and apply ip arp inspection filter NAME vlan X (no DHCP binding exists for static hosts).

    review in the notes →
  105. 2.3 DAI default rate limit on untrusted ports?

    15 ARP packets per second; exceeding it err-disables the port.

    review in the notes →
  106. 2.3 What does ip arp inspection validate src-mac dst-mac ip add?

    Checks that Ethernet and ARP MACs match and rejects invalid IPs (0.0.0.0, broadcast, multicast).

    review in the notes →
  107. 2.3 IP Source Guard?

    Filters every IP packet on an untrusted port whose source IP (and MAC with ip verify source port-security) doesn't match the binding table.

    review in the notes →
  108. 2.3 Order of dependency: DHCP snooping, DAI, IPSG?

    Snooping first (builds the table) → DAI validates ARP → IPSG validates IP.

    review in the notes →
  109. 2.3 Storm control default action and alternatives?

    Drops excess broadcast/multicast/unicast above the threshold. storm-control action trap alerts; action shutdown err-disables.

    review in the notes →
  110. 2.3 storm-control broadcast level 20.00 10.00 means?

    Start dropping broadcast above 20% of bandwidth (rising) and stop when it falls below 10% (falling).

    review in the notes →
  111. 2.3 Two steps for every unused port?

    Shut it down and park it in a dead VLAN (e.g. 777) that isn't routed or trunked.

    review in the notes →
  112. 2.3 Why disable CDP/LLDP on user ports?

    They leak switch model, IOS version, management IP and native VLAN: free reconnaissance.

    review in the notes →
  113. 2.3 Private VLAN port types and who they reach?

    Promiscuous: everyone. Community: its community + promiscuous. Isolated: only promiscuous, not even other isolated ports.

    review in the notes →
  114. 2.3 Private VLAN prerequisite with VTPv1/v2?

    VTP transparent mode.

    review in the notes →
  115. 2.3 How many isolated VLANs per primary VLAN?

    One (but multiple community VLANs).

    review in the notes →
  116. 2.3 switchport protected?

    Protected ports can't forward to other protected ports on the same switch. A lightweight PVLAN edge with local significance only.

    review in the notes →
  117. 2.3 What is an SGT and how big is it?

    A 16-bit Security Group Tag for a device's role in Cisco TrustSec.

    review in the notes →
  118. 2.3 How do devices get SGTs?

    Dynamically via 802.1X or MAB with ISE, or statically by IP, subnet, VLAN or port mapping.

    review in the notes →
  119. 2.3 Two ways SGTs propagate?

    Inline tagging (Cisco Meta Data in the frame) or SXP, which shares IP-to-SGT mappings over TCP.

    review in the notes →
  120. 2.3 Where are SGT policies enforced?

    By SGACLs (typically at egress) or SGT-aware firewalls, defined centrally in ISE.

    review in the notes →
  121. 2.3 PVLAN vs. SGT: the key difference?

    PVLANs are tied to ports and location; SGTs follow the device's identity anywhere in the TrustSec domain.

    review in the notes →
  122. 2.3 Which SCOR v2.0 objective covers VLAN hopping, port security, DHCP snooping, DAI and storm control?

    2.3: Configure network infrastructure security methods. (In v1.1 this material was 2.4/2.5.)

    review in the notes →
  123. 2.3 BPDU Guard vs. Root Guard: what state does the port go into, and how does it recover?

    BPDU Guard: any BPDU puts the port in err-disabled; remove the cause, then shutdown / no shutdown (or an errdisable recovery timer). Root Guard: a superior BPDU puts it root-inconsistent (blocking); it recovers on its own once the superior BPDUs stop.

    review in the notes →
  124. 2.3 Why must Root Guard never go on an access switch's uplink toward the root?

    That port faces the root, so it receives superior BPDUs all the time. Root Guard would block your own uplink. Put Root Guard on the root's downlinks, the ports where a better root should never appear.

    review in the notes →
  125. 2.3 Root Guard and Loop Guard on the same port?

    Not allowed: they're mutually exclusive. On a distribution-to-access trunk: Root Guard on the distribution (root) side, Loop Guard on the access side's root port.

    review in the notes →
  126. 2.3 Clients lose DHCP right after snooping is enabled; the IOS DHCP server is on the same VLAN and the uplink is trusted. Why?

    By default snooping inserts option 82 with giaddr 0.0.0.0, and an IOS DHCP server drops those requests. Fix: no ip dhcp snooping information option on the switch, or ip dhcp relay information trust-all on the server.

    review in the notes →
  127. 2.3 DAI with an ARP ACL: which is checked first, and what does the static keyword change?

    The ARP ACL is checked first, then the DHCP snooping binding table. With ip arp inspection filter NAME vlan X static, the ACL becomes the only check, with an implicit deny at the end.

    review in the notes →
  128. 2.3 Safe order to recover a port err-disabled by BPDU Guard?

    1. Find the reason (show interfaces status err-disabled). 2. Remove the cause (the rogue switch). 3. shutdown then no shutdown. Bring it up with the switch still attached and it err-disables again.

    review in the notes →
  129. 2.3 spanning-tree vlan 10 priority 4096 shows as what priority in VLAN 10, and why?

    4106. PVST+ and Rapid PVST+ add the VLAN ID (the extended system ID) to the configured priority, which is why priorities must be multiples of 4096.

    review in the notes →
  130. 2.3 storm-control broadcast level 20.00 with no falling value: when does forwarding resume?

    The falling threshold defaults to the rising threshold, so broadcast forwarding resumes once traffic drops below 20%.

    review in the notes →
  131. 2.4 Single-device vs. multidevice manager: what's the difference, and why does it matter?

    A single-device manager configures one box at a time (FDM, ASDM, CLI). A multidevice manager pushes one change to many devices (FMC, Security Cloud Control). Beyond a handful of devices, central management is how you stay consistent and auditable.

    review in the notes →
  132. 2.4 FDM vs. FMC?

    FDM (Firewall Device Manager): on-box web GUI for one FTD. FMC (Firewall Management Center): central manager for many FTDs, on-prem appliance or VM. An FTD uses one or the other, not both.

    review in the notes →
  133. 2.4 What is ASDM?

    Adaptive Security Device Manager: a Java GUI that manages one ASA at a time.

    review in the notes →
  134. 2.4 What is Security Cloud Control (SCC)?

    Cisco's cloud-based, AI-assisted, multidevice manager for ASA, FTD (cloud-delivered FMC), Meraki MX, SD-WAN, Multicloud Defense and Secure Access. The evolution of Cisco Defense Orchestrator (CDO).

    review in the notes →
  135. 2.4 A question mentions Cisco Defense Orchestrator (CDO). What should you think?

    Security Cloud Control. SCC is the evolution of CDO; Cisco docs and licensing still use the CDO name in places.

    review in the notes →
  136. 2.4 How does Security Cloud Control manage devices the cloud can't reach directly?

    Through a Secure Device Connector (SDC): a small VM on your network that relays between SCC and the device.

    review in the notes →
  137. 2.4 SCC's three stated goals?

    Simplify operations, enhance security (AI-assisted log analysis), improve clarity (visibility across the estate).

    review in the notes →
  138. 2.4 What is out-of-band change detection in SCC?

    SCC flags any change made directly on a device instead of through SCC, so you can accept or reject it. It's drift detection for the fleet.

    review in the notes →
  139. 2.4 What manages the Catalyst SD-WAN fabric, and what's its gap?

    Catalyst SD-WAN Manager (formerly vManage). It handles SD-WAN connectivity and routing, not unified security policy across firewalls; SCC fills that gap.

    review in the notes →
  140. 2.4 In-band vs. out-of-band management?

    In-band: management shares the production network (simple, less secure, fails with production). Out-of-band: a separate management network or console path (secure, survives outages, costs more). OOB is best practice.

    review in the notes →
  141. 2.4 Why does out-of-band management matter most during an incident?

    A DoS or routing failure that takes down production also takes down in-band access, exactly when you need it. OOB keeps a path to fix things.

    review in the notes →
  142. 2.4 Name three out-of-band constructs on Cisco platforms.

    FTD's dedicated Management interface, an ASA interface with management-only, the IOS XE Mgmt-intf VRF (Gi0/0), and console servers.

    review in the notes →
  143. 2.4 On-prem vs. cloud management: pros and cons?

    On-prem (FMC): full control, data stays local; you maintain it. Cloud (SCC, SaaS): reachable anywhere, scales, Cisco maintains it; depends on internet access, less direct control.

    review in the notes →
  144. 2.4 Mixed ASA, FTD and Meraki MX at 120 sites, remote admins. Which manager?

    Security Cloud Control: multi-platform, multidevice, cloud-reachable from anywhere.

    review in the notes →
  145. 2.5 What is a CIS Benchmark?

    A consensus-based set of secure configuration recommendations for one specific technology, published free by the Center for Internet Security.

    review in the notes →
  146. 2.5 CIS Benchmarks vs. CIS Controls?

    Benchmarks: configuration guides for one product (e.g. IOS XE). Controls: an organization-wide, prioritized set of safeguards. Each benchmark recommendation maps to the Controls it supports.

    review in the notes →
  147. 2.5 Four reasons to use CIS Benchmarks?

    Reduce the attack surface, prevent misconfiguration, standardize configuration across devices, support compliance (PCI DSS, HIPAA, NIST).

    review in the notes →
  148. 2.5 Level 1 vs. Level 2 profile?

    Level 1: practical baseline, clear benefit, shouldn't break operations. Level 2: defense in depth for high-security environments; extends Level 1 and may reduce functionality or performance.

    review in the notes →
  149. 2.5 Automated vs. Manual assessment status?

    Automated: a tool can check pass/fail. Manual: a human must verify.

    review in the notes →
  150. 2.5 Fields of a CIS Benchmark recommendation?

    Title, profile, assessment status, description and rationale, impact, audit procedure, remediation procedure, default value, CIS Controls mapping.

    review in the notes →
  151. 2.5 How are the Cisco network-device CIS Benchmarks organized?

    By the three planes: management (AAA, SSHv2, SNMPv3, NTP auth, logging), control (routing protocol authentication), data (uRPF, ACLs, no source routing).

    review in the notes →
  152. 2.5 Which two Cisco platforms does SCOR 2.5 name for CIS Benchmarks?

    Cisco Secure Firewall Threat Defense (FTD) and Cisco IOS XE. CIS also publishes ASA, IOS XR and NX-OS benchmarks.

    review in the notes →
  153. 2.5 Where do you apply CIS hardening on FTD vs. IOS XE?

    IOS XE: CLI configuration. FTD: mostly platform settings pushed from FMC (or FDM / SCC): management access lists, external authentication, syslog, SNMP, NTP, banners, timeouts.

    review in the notes →
  154. 2.5 What is configuration drift?

    The gap between the approved hardened baseline and what's actually running, caused by later changes, upgrades or quick fixes.

    review in the notes →
  155. 2.5 The benchmark-to-fleet loop?

    Harden (golden config) → audit (CIS-CAT, scanners) → detect drift (change logs, out-of-band change detection, diffs) → remediate → repeat.

    review in the notes →
  156. 2.5 Do CIS Benchmarks replace patching?

    No. They're one component. A hardened device running vulnerable software is still vulnerable: pair benchmarks with patching and vulnerability management.

    review in the notes →
  157. 2.6 Authentication, authorization, accounting in one line each?

    Authentication: who are you? Authorization: what may you do? Accounting: what did you do?

    review in the notes →
  158. 2.6 Device administration vs. network access: which protocol fits each?

    Device administration (admins logging in to network devices): TACACS+. Network access (users and endpoints joining via 802.1X, MAB, VPN, wireless): RADIUS.

    review in the notes →
  159. 2.6 TACACS+ transport and port?

    TCP 49.

    review in the notes →
  160. 2.6 RADIUS ports?

    UDP 1812 authentication/authorization, UDP 1813 accounting. Legacy: 1645 / 1646.

    review in the notes →
  161. 2.6 What does each protocol encrypt?

    TACACS+: the entire packet body (header readable). RADIUS: only the password attribute; usernames and other attributes are cleartext.

    review in the notes →
  162. 2.6 Which protocol separates AAA, and why does it matter?

    TACACS+ separates authentication, authorization and accounting, which enables per-command authorization. RADIUS combines authentication and authorization in one Access-Accept.

    review in the notes →
  163. 2.6 What does aaa new-model do, and what must you do first?

    Switches the device to the AAA framework: every login path is now controlled by AAA. Create a local privilege-15 account first so you can't lock yourself out.

    review in the notes →
  164. 2.6 Read: aaa authentication login TAC group tacacs+ local

    Try the TACACS+ servers first; use the local database only if no server answers.

    review in the notes →
  165. 2.6 When does a method list move to the next method?

    Only when the current method returns an error (no server answered). A reject (wrong password from a reachable server) is final.

    review in the notes →
  166. 2.6 Named vs. default method list?

    A named list applies only where it's referenced (login authentication NAME on a line). The default list applies to every line that doesn't name one, including the console.

    review in the notes →
  167. 2.6 A TACACS+ user logs in but enable fails. Why, and three fixes?

    Authentication isn't privilege: the user lands at priv 1. Fix with enable secret, aaa authentication enable default group tacacs+ enable, or aaa authorization exec so the server returns priv 15.

    review in the notes →
  168. 2.6 Why ip tacacs source-interface Loopback0?

    Requests always come from one predictable IP, which must match the network device entry on the server. A mismatch looks like a timeout or a key error.

    review in the notes →
  169. 2.6 Is authorization applied on the console by default?

    No. IOS skips authorization on the console unless you add aaa authorization console, so a broken server can't lock you out of the last-resort path.

    review in the notes →
  170. 2.6 What does aaa authorization network do for 802.1X?

    Lets the switch apply what ISE returns: VLAN, downloadable ACL, SGT. Without it, those attributes are ignored.

    review in the notes →
  171. 2.6 What is CoA and what enables it on IOS?

    Change of Authorization (RFC 5176): the RADIUS server changes a live session (reauthenticate, reassign, disconnect). Enabled with aaa server radius dynamic-author; ISE uses UDP 1700 by default, the RFC port is 3799.

    review in the notes →
  172. 2.6 The three layers of AAA failure?

    Reachability (can the device reach the server on TCP 49 / UDP 1812?), device trust (shared key, device registered, source IP), user (credentials and permissions).

    review in the notes →
  173. 2.6 debug tacacs: Opened TCP/IP handle then Invalid AUTHEN/START ... (check keys)?

    Shared key mismatch. The server was reachable (the connection opened) but the reply decrypted to garbage.

    review in the notes →
  174. 2.6 debug tacacs: GETPASS then status = FAIL?

    Bad credentials. The server understood the request and rejected the user. The local fallback won't be tried.

    review in the notes →
  175. 2.6 Connection timed out vs. Connection refused to port 49?

    Timed out: nobody answered (wrong IP, host down, firewall dropping). Refused: the host answered with a reset; the TACACS+ service isn't listening.

    review in the notes →
  176. 2.6 What does test aaa group tacacs+ USER PASS legacy prove, and what doesn't it test?

    That the server group can authenticate the user, without changing login config. It ignores line configuration, so it can't catch an unapplied or misspelled method list.

    review in the notes →
  177. 2.6 RADIUS shared key mismatch: what does the switch usually see?

    Often just timeouts (the server drops the request, or the reply fails the authenticator check). The server's log (e.g. ISE Live Logs) shows the real reason.

    review in the notes →
  178. 2.6 802.1X fails and ISE Live Logs show nothing at all. First suspects?

    The switch never reached ISE: server marked DEAD, routing or ACL blocking UDP 1812, or 802.1X not enabled (dot1x system-auth-control). Check show aaa servers.

    review in the notes →
  179. 2.7 What three properties do secure management protocols add over the old cleartext ones?

    Confidentiality (encryption), integrity (tamper detection) and authentication (proof of who is talking). Then restrict who can reach them and give them trusted time.

    review in the notes →
  180. 2.7 SNMP: MIB vs. OID?

    The MIB is the hierarchical database of managed objects; an OID is the dotted path to one object in it, e.g. 1.3.6.1.2.1.1.5.0 = sysName.

    review in the notes →
  181. 2.7 What does the trailing .0 on an OID mean?

    The instance of a scalar (single-value) object. snmpget needs it (...1.1.5.0); snmpwalk walks a subtree with or without it.

    review in the notes →
  182. 2.7 USM vs. VACM in SNMPv3?

    USM (User-based Security Model): users and their authentication and privacy keys. VACM (View-based Access Control Model): views and what each group may read or write.

    review in the notes →
  183. 2.7 SNMPv3 IOS keywords for the three security levels?

    noauth = noAuthNoPriv, auth = authNoPriv (HMAC), priv = authPriv (HMAC + AES/DES encryption).

    review in the notes →
  184. 2.7 The four SNMPv3 objects and their order?

    ACL (which hosts) → view (which MIB subtree) → group (minimum level, read/write views, ACL) → user (group membership and keys).

    review in the notes →
  185. 2.7 What does the SNMPv3 group's security level set?

    The minimum level. A group created with priv refuses requests at authNoPriv or noAuthNoPriv.

    review in the notes →
  186. 2.7 What is the SNMPv3 engine ID used for, and what happens if it changes?

    Passphrases are localized: hashed with the engine ID to make the real keys. If the engine ID changes, existing users stop working and must be recreated.

    review in the notes →
  187. 2.7 show snmp user returns %SNMP agent not enabled even though views and groups exist. Why?

    On IOS XE, only the first user (or community) starts the SNMP agent. Verify views and groups with show run | include snmp-server until then.

    review in the notes →
  188. 2.7 Fastest check when an SNMPv3 user can read but not write?

    show snmp user: look at Group-name. A read-write user created in the read-only group has no write view.

    review in the notes →
  189. 2.7 Net-SNMP: Authentication failure (incorrect password, community or key)?

    Wrong authentication passphrase or protocol (-A / -a).

    review in the notes →
  190. 2.7 Net-SNMP: Timeout: No Response with SNMPv3. Likely causes?

    Wrong privacy passphrase, source not permitted by the SNMP ACL (denies are silent), or no matching user.

    review in the notes →
  191. 2.7 Why is read-write SNMP equivalent to configuration access?

    With a write view, snmpset can rename the device (sysName), shut interfaces (ifAdminStatus = 2) or trigger config copies. Give RW only to tools that need it.

    review in the notes →
  192. 2.7 What is YANG?

    A data modeling language (RFC 7950) that defines the structure, types and constraints of configuration and state. YANG is the "what"; NETCONF and RESTCONF are the "how".

    review in the notes →
  193. 2.7 Standard vs. native YANG models?

    Standard (ietf-*, OpenConfig): vendor-neutral, portable, fewer features. Native (Cisco-IOS-XE-native): every IOS XE feature, Cisco only.

    review in the notes →
  194. 2.7 NETCONF: RFC, transport, port, encoding?

    RFC 6241, SSH, TCP 830, XML.

    review in the notes →
  195. 2.7 What gives NETCONF transactions?

    The candidate datastore plus <validate> and <commit> (and <lock>): stage a change set, check it, apply it as one. RESTCONF has no candidate or commit.

    review in the notes →
  196. 2.7 What does a NETCONF <hello> contain?

    The device's capabilities: protocol versions (base 1.0 / 1.1), features (writable-running, validate, rollback-on-error, notifications) and every supported YANG module.

    review in the notes →
  197. 2.7 RESTCONF: RFC, transport, port, encodings?

    RFC 8040, HTTPS, TCP 443, JSON or XML (application/yang-data+json / +xml).

    review in the notes →
  198. 2.7 RESTCONF HTTP methods and what they do?

    GET read, POST create, PUT create or replace, PATCH merge, DELETE remove.

    review in the notes →
  199. 2.7 RESTCONF URL shape?

    https://<device>/restconf/data/<module>:<container>, e.g. /restconf/data/ietf-interfaces:interfaces.

    review in the notes →
  200. 2.7 Enable NETCONF vs. RESTCONF on IOS XE?

    NETCONF: netconf-yang. RESTCONF: ip http secure-server + restconf. NETCONF needs no HTTP server.

    review in the notes →
  201. 2.7 How do you know RESTCONF and NETCONF are ready to answer?

    show platform software yang-management process: nginx and confd Running (RESTCONF), ncsshd Running (NETCONF).

    review in the notes →
  202. 2.7 A RESTCONF script fails with JSONDecodeError ... (char 0) right after enabling it. Why?

    The YANG processes weren't ready, so the router returned an HTML error page, not JSON. Check the processes; print the status code before parsing.

    review in the notes →
  203. 2.7 Four ways to harden RESTCONF on IOS XE?

    no ip http server, ip http tls-version TLSv1.2, a CA-signed certificate (ip http secure-trustpoint), ip http access-class ipv4 <ACL>; plus dedicated AAA accounts.

    review in the notes →
  204. 2.7 How does the FMC REST API authenticate requests?

    POST credentials to the token endpoint, then send the token in the X-auth-access-token header. Tokens expire (30 minutes) and can be refreshed a limited number of times.

    review in the notes →
  205. 2.7 NTP stratum 1 vs. 16?

    1: directly attached to a reference clock, most authoritative. 16: unsynchronized. Each hop adds 1.

    review in the notes →
  206. 2.7 In NTP client/server mode, who authenticates whom?

    The client authenticates the server: it accepts time only if the reply is signed with a trusted key.

    review in the notes →
  207. 2.7 The four commands for authenticated NTP on a client?

    ntp authenticate, ntp authentication-key <n> hmac-sha2-256 <secret>, ntp trusted-key <n>, ntp server <ip> key <n>. All four are required.

    review in the notes →
  208. 2.7 What does ntp master 3 do?

    Makes the device serve time from its local clock at stratum 3 (reference 127.127.1.1). Its clients become stratum 4.

    review in the notes →
  209. 2.7 Why must you clock set close to the right time before NTP?

    NTP won't step a clock more than about 1000 seconds off (the panic threshold). Also: clock set is privileged EXEC, not config mode.

    review in the notes →
  210. 2.7 show ntp associations: what do * and ~ mean, and what is reach 377?

    * = system peer (synced to it). ~ = configured. reach 377 (octal) = all of the last 8 polls answered.

    review in the notes →
  211. 2.7 debug ntp all shows SHA256-Match: 0. Meaning?

    The HMAC didn't verify: the key number, algorithm or secret differ. The client discards the time.

    review in the notes →
  212. 2.7 show ntp packets: Out climbing, In stays 0?

    The server isn't answering: unreachable, UDP 123 filtered, or not serving time.

    review in the notes →
  213. 2.7 RFC 5424 vs. RFC 5425?

    5424: the structured syslog message format. 5425: syslog over TLS, TCP 6514.

    review in the notes →
  214. 2.7 logging trap warnings sends which severities?

    Levels 0 to 4 (emergencies through warnings): the chosen level and everything more severe.

    review in the notes →
  215. 2.7 crypto pki authenticate vs. enroll vs. import?

    authenticate: trust the CA (checked against the pinned fingerprint). enroll: create this device's certificate request. import: install the signed device certificate.

    review in the notes →
  216. 2.7 Why does secure syslog depend on NTP?

    TLS certificates have validity dates. A wrong clock makes them look not-yet-valid or expired, and the TLS session fails.

    review in the notes →
